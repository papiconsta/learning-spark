Lazy evaluation

Transformations only build a plan. Nothing runs until you call an action.

A transformation (filter, select, groupBy) returns a new DataFrame describing what to compute. An action (count, show, collect, write) makes Spark optimize the whole plan and execute it.

from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.master("local[*]").appName("learning-spark").getOrCreate()

df = spark.range(1_000_000)                  # transformation: nothing runs yet
evens = df.filter(F.col("id") % 2 == 0)      # still nothing
print(evens.count())                         # action: now Spark runs the job
500000
vs pandas

In pandas every line runs immediately. In Spark you're building a query, closer to writing SQL than to calling NumPy.

Key idea

Because Spark sees the whole plan first, it can reorder and combine steps, e.g. push a filter down into the file scan.

Common mistake

Calling .count() or .show() after every step "to check" re-runs the whole plan each time.

Changed since the book

The book uses sqlContext in places; in Spark 4 always use SparkSession.

Tip

Use df.explain() to see the physical plan without running anything.

Narrow vs wide transformations

read→ filter (narrow)→ groupBy (wide · shuffle)→ count
A shuffle splits the job into stages.
NarrowWide
Partitions1 input → 1 outputmany inputs → many outputs

Which of these triggers a Spark job?

Which transformation causes a shuffle?
