Architecture: driver, executors, cluster manager

One driver plans the work; many executors do it; a cluster manager hands out machines.

Driver
runs your main(), builds the plan, schedules tasks ⇄ Cluster manager
YARN · Kubernetes · standalone → Executor 1 Executor 2 Executor N
Executors only run the code the driver gives them and report results back.
  • The driver is your Python process. It holds the SparkSession and decides what runs where.
  • Executors are JVM processes on worker machines. Each runs tasks on its own partitions.
  • In local mode (what we use) driver and executors are just threads on your laptop. The code is identical to what you'd run on a cluster.
Changed since the book

The book lists Mesos as a cluster manager. It is gone in Spark 4; Kubernetes is the other mainstream choice besides YARN.

vs pandas

PySpark code doesn't run in Python. Your calls build a plan that the driver ships to JVM executors, so Python lambdas and UDFs are the slow path (more in later chapters).

SparkSession and your first DataFrame

The SparkSession is the single entry point; a DataFrame is an immutable, distributed table with a schema.

from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.master("local[*]").appName("learning-spark").getOrCreate()

my_range = spark.range(1000).toDF("number")
my_range.printSchema()
print(my_range.rdd.getNumPartitions())
root
 |-- number: long (nullable = false)

16
  • Schema: column names and types. Here one long column.
  • Partition: a chunk of rows that one task processes. 16 here, because local[*] uses every core on this machine.
  • DataFrames are immutable. Every operation returns a new DataFrame; nothing is modified in place.
Common mistake

Partitions are the unit of parallelism. One partition means one task at a time, no matter how many cores or executors you have. Too many tiny partitions waste time on scheduling.

Transformations vs actions, and lazy evaluation

Transformations describe; actions execute. Spark optimizes the whole plan before running anything.

div_by_2 = my_range.where("number % 2 = 0")   # transformation: no job, no output
div_by_2.count()                               # action: runs a job
500
TransformationAction
Returnsa new DataFramea Python value, console output, or files
Runs a job?No (lazy)Yes
Exampleswhere, select, groupBy, joincount, show, collect, write
Key idea

Because Spark sees the whole plan first, it can optimize end to end. Example: predicate pushdown moves a filter down into the file scan so less data is read at all.

Common mistake

Calling count() or show() after every step to "check" re-runs the whole plan each time. Use explain() or printSchema(), which don't run a job.

Predict: does spark.range(10**12).where("number % 2 = 0") take long?

No. It's a transformation, so it returns instantly. Only an action would try to process the trillion rows.

Narrow vs wide transformations (shuffles)

Narrow = each partition stands alone and is pipelined in memory. Wide = data moves between partitions (a shuffle).

scan→ filter (narrow)→ groupBy (wide · shuffle)→ sum
A shuffle is a stage boundary: Spark writes shuffle data to disk and sends it over the network.
NarrowWide
Partitions1 input → 1 outputmany → many
Examplesfilter, select, withColumngroupBy, join, orderBy, distinct
Costcheap; chained filters run pipelined in memoryexpensive: disk + network

You can see the shuffle in the physical plan. It appears as Exchange:

flights.where("count > 10").groupBy("DEST").sum("count").explain()
== Physical Plan ==
AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[DEST#7], functions=[sum(count#9L)])
   +- Exchange hashpartitioning(DEST#7, 200), ENSURE_REQUIREMENTS
      +- HashAggregate(keys=[DEST#7], functions=[partial_sum(count#9L)])
         +- Project [DEST#7, count#9L]
            +- Filter (isnotnull(count#9L) AND (count#9L > 10))
               +- Scan ExistingRDD[DEST#7,ORIGIN#8,count#9L]

Read it bottom-up: scan → filter → partial sum on each partition → Exchange (shuffle) → final sum. Spark pre-aggregates before the shuffle (partial_sum) so less data moves.

Tip

The 200 in hashpartitioning(DEST, 200) is spark.sql.shuffle.partitions, whose default is 200. It is often wrong for small local data (200 tiny tasks) and for very large data. You'll tune it in Chapter 19.

Changed since the book

AdaptiveSparkPlan is Adaptive Query Execution (on by default since Spark 3.2). It adjusts shuffle partitions and join strategies at runtime, so real plans differ from the book's.

End-to-end: DataFrame API and SQL are the same thing

Both compile to the same optimized plan, so pick whichever reads better.

The book loads CSVs with spark.read.option("inferSchema","true").option("header","true").csv(...). Its data isn't in this repo, so here is the same query on a small inline table:

data = [("United States","Romania",15), ("United States","Croatia",1),
        ("United States","Ireland",344), ("Egypt","United States",15),
        ("United States","India",62), ("India","United States",69)]
flights = spark.createDataFrame(data, ["DEST", "ORIGIN", "count"])
flights.createOrReplaceTempView("flights")
(flights.groupBy("DEST")
        .agg(F.sum("count").alias("total"))
        .orderBy(F.desc("total"))
        .show())
spark.sql("""
    SELECT DEST, SUM(count) AS total
    FROM flights GROUP BY DEST ORDER BY total DESC
""").show()
+-------------+-----+
|         DEST|total|
+-------------+-----+
|United States|  422|
|        India|   69|
|        Egypt|   15|
+-------------+-----+
Key idea

Both versions go through the same optimizer, so there's no performance reason to prefer one. You can mix them freely with temp views.

Tip

While a job runs, the Spark UI is at localhost:4040. Use it to see jobs, stages, tasks and shuffles. Chapter 18 covers it in depth.

Quiz ·

Which call actually starts a Spark job?
count() is an action. The others only extend the plan.
You have 1 partition and 100 executors. How much parallelism do you get?
Parallelism is bounded by the number of partitions. Extra executors sit idle.
Which of these causes a shuffle?
Rows with the same key must land in one partition, so groupBy is wide. The others work on each partition independently.
In explain() output, what marks the shuffle?
Exchange is Spark's physical shuffle operator.
Same query in the DataFrame API and in SQL: which is faster?
Both are optimized by the same engine. Compare plans with explain() to confirm.
